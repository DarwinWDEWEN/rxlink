- 域名优先级解析一条 SQL 成立：`probe_resolve('AbC123','s.probe.test')` → `from-domain`；`('AbC123','')` → `from-global`；`('AbC123','other.domain.test')` → `from-global`。与 shlink `findOneWithDomainFallback` 语义一致，无 `LOWER()` 性能坑。

## 判定

- **原方案 1（Edge Function 直接承接跳转热路径）不成立**：项 2b FAIL 是硬伤——只要函数返回 3xx 且带 `Location`，平台就会代替客户端跟随，客户端要么拿到被跟随后的内容（相对/内部目标），要么直接超时（外部目标 + 未开公网出口）。`301/302` 语义在这个网关上拿不到，与是否开 JWT、用哪种部署方式无关。
- **项 2a PASS**：免 JWT 公开 GET 成立，所以「函数能被终端用户直接访问」没问题，问题只在**响应形态**。
- 退路候选经 2026-11-06 文档调研 + 项 2c 实测后收敛（详见下一节「官方口径核对」与 `docs/tech-framework.md` §6.1）：
  ① **C：跳转层用「函数计算 FC 函数 + 自定义域名」——已实测成立，建议就此定案**：`http://example.com/r/AbC123` 拿到**真 302 + `Location`**，`host` 就是短链域名、`pathname` 保留原始短码、`x-forwarded-for` 带真实客户端 IP ⇒ 跳转语义、多域名归属、访问日志三项前提同时满足，且不需要 CDN。Supabase 退为纯数据面（REST/RPC）。剩余缺口只有 HTTPS 证书（见项 2c-T2）。
  ② **D：自建边缘（Caddy/Nginx + Go）承接短链域名跳转**，直连 Supabase 的 REST/RPC——语义同样干净，官方背书更少、运维面最大，作 C 的兜底。
  ③ **B：软跳转（函数返回 200 + HTML，meta refresh / `location.replace`）**——立刻可落地、不影响统计链路，但丢 SEO 权重传递、命令行/爬虫行为不直观，只在 C/D 都不成立时用。
  ✗ **A（CDN 改写响应状态码）与 A'（ESA 边缘函数发 302）已被文档否掉**：CDN 的「重写访问 URL」只改请求 URL，无「改写源站响应状态码」能力；ESA 边缘函数自己就代客户端跟随 302 且无开关。
- **仍未闭合的两个变量**：① Supabase 侧的「挂住/跟随」与 FC 默认域名的「秒回 400」不是同一表现，**是否同一策略要工单定性**（引用 `X-Fc-Error-Type: InvocationError` 那条响应体最有说服力）；② 当前 Supabase 项目**未开通公网访问**，`loc=ext` 的超时可能只是出不去外网——开通后复测 `mode=s302&loc=ext` 可区分。两者都不影响结论方向（自定义域名是唯一被官方指路的路径），只影响工单措辞与「跳转层能否留在 Supabase」。
- 项 4/5/7 全过 ⇒ §5.3 统计链路（fire-and-forget 写 UNLOGGED inbox + pg_cron 批量物化 + slot 计数）**可以按原设计落地**，且 pg_cron 只跑纯 SQL 就够，不需要 pg_net。
- 项 3b/3c：50 并发时纯响应都排到 p95≈0.7s，跳转层如果留在函数里，QPS 上限要先拿到配额数值才能估——这一项现在变成**独立于 2b 的第二个风险**。
- 项 8/9/10/12/13 已改写 §4 的 DDL 模板、§4.1 权限收口与 RPC 约定（见 `docs/tech-framework.md`）。

## 项 2b 的官方口径核对（2026-11-06 文档调研，都有出处）

1. **ADB Supabase 边缘函数文档对 3xx/`Location`/重定向零字**：唯一示例是 `Deno.serve` + `req.json()` + `new Response(JSON.stringify(...))`，测试结论写死「响应状态码为 200」，curl 示例是 `curl -L -X POST`；既没有「支持跳转」也没有「不支持 3xx」的条款（[using-edge-functions-in-analyticdb-supabase](https://help.aliyun.com/zh/analyticdb/analyticdb-for-postgresql/using-edge-functions-in-analyticdb-supabase)、[Supabase CLI 使用指南](https://www.alibabacloud.com/help/zh/analyticdb/analyticdb-for-postgresql/supabase-cli-usage-guide)）。
2. **上游 Supabase 把 3xx 列为正常能力**：「3XX Redirect: Your Edge Function used the `Response.redirect()` API … normal response when implementing authentication flows or **URL forwarding**」（[supabase.com/docs/guides/functions/status-codes](https://supabase.com/docs/guides/functions/status-codes)）⇒ 我们的用法不怪异，是阿里云这层实现/策略与上游不一致。**这是工单最有力的一句话。**
3. **函数计算官方公告给了原因和解法**：2025-04-01 起，新建函数用 **HTTP 触发器默认公网域名 `*.<region_id>.fcapp.run`** 触发外部 3xx「均会被阻断」，返回 **400 `ExternalRedirectForbidden`**，解决方案原文是**「如果您需要继续使用重定向跳转能力，请为函数绑定自定义域名」**（[公告](https://help.aliyun.com/zh/functioncompute/fc-3-0/product-overview/forbidden-to-use-the-default-public-network-domain-name-of-function-compute-to-redirect-to-the-outside-of-the-station)）。我们的 Edge Function 实测就跑在 `edge-fc-*.cn-hangzhou-vpc.fcapp.run` 上 ⇒ **高度相关**；但观测症状不同（是被跟随/挂住，不是 400），且公告只覆盖「默认公网域名」，VPC 内网域名口径未提 ⇒ 是否同一策略，只能工单确认（**这里是推测**）。
4. **ESA 边缘函数同样代客户端跟随 302**：「当边缘函数生成 302 重定向响应时，边缘节点自动代理客户端请求目标地址并返回最终内容，该机制通过减少跳转交互来提升响应速度」，未给关闭开关（[document_detail/2879081](https://help.aliyun.com/document_detail/2879081.html)）⇒ 「边缘自动跟随 302」是阿里云边缘的一贯设计取向，不是 ADB Supabase 独有。
5. **CDN 侧两条相关事实**：回源 301/302 跟随是**默认关闭**的可选开关（[配置回源301/302跟随](https://help.aliyun.com/document_detail/281143.html)、参数 `follow_302`）；「重写访问 URL」只作用于**请求** URL，`Redirect` 模式默认给客户端 302（支持 303/307，改状态码要工单）、`break` 模式内部改写回源路径且客户端 URL 不变，**文档没有任何「改写源站响应状态码」的能力**（[规则文档](https://help.aliyun.com/zh/cdn/user-guide/create-an-access-url-rewrite-rule)）⇒ 原设想的「函数回 200+Location、CDN 把状态改成 302」**不成立**。
6. **Kong 不背这个锅**：2.8 Proxy Reference 原文「Kong receives the response from the upstream service and sends it back to the downstream client in a streaming fashion」，无跟随逻辑（[docs.konghq.com/gateway/2.8.x/reference/proxy](https://docs.konghq.com/gateway/2.8.x/reference/proxy/)）；nginx 默认也不跟随（要 `proxy_intercept_errors + error_page + proxy_pass $upstream_http_location` 才实现）。与我们实测「302 不带 Location 原样返回」互相印证。
7. **没有公开先例**：检索 supabase/supabase、supabase/edge-runtime issues 与中英文社区，未找到任何人报告过「Supabase Edge Function 的 redirect 被吞/被跟随」⇒ 这条是我们的独占实测，工单里要附复现命令。

**选型影响**：跳转层唯一有官方依据的真 302 路径是「**FC 函数绑定自定义域名**」（方案 C，见 `docs/tech-framework.md` §6.1），A/A' 已按文档否掉。
